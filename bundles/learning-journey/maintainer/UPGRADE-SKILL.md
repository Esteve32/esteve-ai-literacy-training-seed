# Upgrade and export the training journey

## Required inputs and authority
Use https://github.com/Esteve32/esteve-ai-literacy-training-seed as the training distribution single source of truth. DB11 remains the authority for its original skill bodies; GitHub holds reviewed portable derivatives, not a competing private library. Confirm exact branch/base SHA, programme, bounded goal, approved source allowlist, destination and human review gate. Read local README/agent/build/safety instructions. Verify the active GitHub login; expected login Esteve32. Use the existing authorised connection where possible. The owner's private sign-in email is not needed for repository operations; retrieve it only from an approved private operator profile when authentication requires it. Never write sign-in emails or secrets to this public skill or participant exports. Do not guess malformed dictation. If the connection identifies a different user, stop and ask rather than changing accounts silently.

## Refresh protocol
1. Inspect current main, overlapping branches/PRs and relevant progress issue when available. State tiny goal, file plan, untouched scope and stop conditions. Do not force-reset or overwrite another person's edits. New course selection is not permission to export private sources or all DB11 bodies.
2. For repository-only refresh, use current checked-out approved source. For “latest DB11”, use an authorised Notion connection or owner-provided dated export. Discover by relevant titles/descriptions; load only selected cores. Reuse the canonical DB11 README once. Match stable identity; do not infer verification from In Use. Reopen unresolved review gaps. Missing access = source freshness Unknown/blocked, not no updates.
3. Selected external roles currently reviewed: 11.19 clarification UX and 11.43 personal style calibration. Live source pages must be resolved in the authorised private workspace; private URL/ID maps do not belong here. If identity cannot be resolved unambiguously, ask for the exact source. Compare live body hashes and lifecycle to source-review.json. Record the real source revision/capture time and hash; never fabricate a timestamp, checksum or verification badge.
4. Show semantic differences and separate reusable logic from local databases, people, examples and account settings. Preserve privacy, review and send/write gates. Use generic role/input/output contracts, not blanket removal of safety-relevant context. An internal-only source requires a bounded adaptation and rights review; access alone does not permit raw export. New library candidates need explicit scope and rights approval; never claim all DB11 is included.
5. Propose the exact source/adaptation/test diff. The human's scoped instruction may authorise those changes; ask again only for new scope or material risk. Keep 11.19's native-choice-or-lettered-fallback contract, one decision at a time, free-text steering, action learning, evidence checking, private calibration, Stop and non-observation self-study. Keep personal profiles, sign-in email and private mappings outside GitHub and ZIPs. Do not start a participant log or analytics pipeline.
6. Update existing modules/templates; do not make a new competing skill copy. Change version deliberately for learner-visible behaviour and maintain CHANGELOG.md. Update source-review.json only after an actual review; do not auto-rebaseline hashes to hide drift. Preserve unrelated source files, existing packs and earlier review history.
7. From the repository root run build.py, build.py --check and unittest discovery as documented in README. The builder refreshes the entire existing public library export in a temporary copy, validates its dependencies and makes one training ZIP. On any stale/malformed/missing source or privacy failure: block distribution, retain previous evidence, repair within scope and rerun. Do not label a failed/old ZIP latest. Inspect full changed-file diff, ZIP inventory, unsafe paths, manifest hashes and learner/facilitator separation.
8. Behavioural tests need a real target agent, separate from static checks. Ask whether the human wants a fresh-agent trial; do not delegate or launch sessions unless explicitly authorised. Do not label an internal simulation a work-Copilot test. Use tests/BEHAVIOUR.md with synthetic input; obtain separate consent for participant observation. Keep real observations private. No performance/diagnostic ranking or fabricated results.
9. Push a bounded review branch using the verified GitHub connection, then open a PR to main. Pushing is not merge, publishing a release, default-branch installation or deployment approval. Do not alter protected branches or account settings. Inspect CI status and distinguish queued/passed/failed/unavailable. The workflow rebuilds on repository source changes but does not fetch Notion or upload Drive.
10. Deliver the exact ZIP and SHA256 plus version and source/validation limitations. For Drive, request the exact folder only if asked to upload, use a separately authorised write connection, and read back its version/hash before claiming replacement. Otherwise give the file for manual upload. Do not broaden Drive sharing, store private calibration or claim an old copy updated automatically.

## Output contract

Include base/head commit and PR, actual mechanical test result, source-review coverage/capture dates, behavioural/target-product status, ZIP hash and privacy/rights gaps. Revert the isolated branch commit or restore the preceding versioned ZIP if required; no destructive force push. Do not infer result acceptance from a completed build.

No voice control: offer typing with no penalty. Failed build: do not distribute. Repeated AI mismatch: preview a small instruction patch, require approval, retry with evidence and stop blind loops. No token/credit or universal compatibility promises.
